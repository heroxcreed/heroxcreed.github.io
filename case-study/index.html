1. Background

1.1 The codebase

tt-metal is the C++ stack for Tenstorrent's TT accelerators. For the purposes of this document the relevant layers are:

  • Host-side program factories (*_program_factory.cpp) — compiled into the ttnn wheel. They decide the work split (how many cores, how many tiles per core), allocate the circular buffers (CBs), and pass compile-time defines and runtime arguments to the kernels.
  • Device kernels (device/kernels/*.cpp) — JIT-compiled for the target. Dataflow kernels issue NoC reads/writes by page id; compute kernels operate on 32×32 tiles held in L1 CB pages or in DST registers, with an explicit MATH↔PACK handshake (tile_regs_acquire/commit/wait).

Two properties of that design produce most of the defects below. First, an index that is correct in one indexing space and wrong in another (global vs core-local channel; absolute W coordinate vs face-local element count; logical shape vs padded shape) is silently wrong — the kernel still runs, still returns a tensor, and the tensor is wrong. Second, an out-of-range page id is a wild read rather than a fault, and a write that runs past the end of a CB page or a ROW_MAJOR buffer damages whatever the allocator placed next.

1.2 Why this op family

moreh/* is a port of a large operator set (softmax/softmin layer norm/norm family, optimizer kernels adam/sgd, nll_loss and its backward, arange, group_norm, getitem, …) onto the TT tiling model. It is a good place to work for three reasons: the operators have unambiguous references (PyTorch / torch.nn.functional), the alternative implementations are in the same repository (so "what is the intended invariant here?" is answerable by reading a sibling), and the failure modes are concrete — a wrong group index, a wrong exponent unit, a bound that over-runs a page.

Some of the defects I fixed were seeded by the repository's own static-audit issue: #51278 — "[ttnn/moreh] 13 defects: 3 missing CB allocations, 2 softmin max-subtraction slips, out-of-bounds arange writer" (filed by a Tenstorrent engineer, still open). The item numbers below (item 3, items 6, 7, …) are theirs, not mine — I am not claiming discovery of those items. What is mine in those PRs is the root-cause analysis down to the line, the simulator reproduction, the regression tests, and the fix as merged. Two further defects came from my own investigation, filed as issues I authored (§2.4, §2.8).

Of the 13 items in #51278, six PRs below address nine (1, 2, 3, 5, 6, 7, 11, 12, 13). Items 4 and 8–10 are untouched; 8–10 are one bug seen from three angles (never-allocated scratch CBs).

1.3 The environment

  • ttnn 0.78.0 (installed wheel) + ttsim, the Blackhole simulator. No silicon.
  • Kernel changes were exercised by rebuilding only the kernel under test and keeping the rest at main, with a fresh TT_METAL_CACHE per variant, so a red/green pair cannot be contaminated by a stale JIT artifact.
  • Host-side factory changes cannot be exercised that way when the wheel's own host code is what changed; §3.2 describes the three strategies I used instead, including the case where I could only offer a static proof and said so.

2. Findings

Each section gives the symptom, the root cause at the line, the fix, the measurement, the maintainer feedback, and — where relevant — the limits I stated in the PR myself.

2.1 #56200 — moreh_nll_loss_step2: unguarded weight read + a loop bound in the wrong space (items 6 and 7)

Status: merged (9d2c9aa, 2026-09-16) · labels applied by the repo's triage: pr-priority:p1, pr-risk:high, pr-complexity:medium · 3 files, +155/−9

Symptom. Two independent reader defects in the step-2 kernel of weighted/unweighted NLL loss. For a target that equals ignore_index (or is negative/out of range), the weighted 2d path performed a wild NoC read; for rank-3 inputs wider than one face, the per-face loop iterated past the targets that were actually loaded, and past the end of the CB page for W > 1024. The existing nightly test could not see either: its only 3-D shape was [5, 6, 7], where W < FACE_WIDTH makes the (wrong) bound accidentally right, and its targets came from torch.randint(0, C, …) with ignore_index ∈ {0, 1}, so the ignored/OOR path was never taken.

Root cause (a). The #if defined(WEIGHT) block sits outside the target-validity branch: reader_..._step2_2d.cpp, pre-fix L84, and the page id is computed unconditionally at L85 — uint32_t noc_id = target_val / TILE_WIDTH;. For the ignore default (-100) or any negative target, that is an unsigned division of a negative int32 (-1 → 0x7FFFFFFF; -100 → 134217727), i.e. a read hundreds of megabytes past the weight tensor. The garbage lands in tmp_weight, which had no else-zero, so the compute kernel's mul_tiles(tmp1, tmp_weight) turned a correctly-zeroed contribution into 0 × garbage — or into NaN when the garbage bit pattern is Inf/NaN. The in-tree 4d reader of the same op has the right invariant (weight lookup nested inside the validity check, with an else-zero) — pinned blob, L63–L74.

Root cause (b). reader_..._step2_3d.cpp, pre-fix L78: uint32_t idx_max = std::min(w + FACE_WIDTH, W); mixes an absolute W coordinate with a face-local element count. Only 16 target int32s are loaded per work unit (NOC_MINIMUM_READ_SIZE), and idx is consumed as a face-local index; so for w > 0 the loop ran past the loaded targets, and for W > 1024 it wrote tmp_input_l1_ptr[1024…W-1] — beyond a CB page that holds exactly TILE_HW = 1024 elements — into the neighbouring CBs.

Fix. Gate the weight read on validity and give the ignored case a deterministic zero, matching the 4d reader: new guard at R88, block re-entered under the guard at R82, else-zero for tmp_weight at R83. Bound the loop by what this face actually holds: R78, idx_max = std::min(FACE_WIDTH, W - w). Plus regression tests: test_moreh_nll_loss_negative_ignore_index_2d and test_moreh_nll_loss_step2_3d_multi_face, extended from 2 to 10 parametrizations.

Measurement (ttsim, Blackhole, ttnn 0.78.0 — no hardware). Because these are wild-read/page-overrun defects and the simulator returns zeros for unallocated memory, the damage is not numerically observable on every path. The genuinely red/green pair, per the PR's own comment, is test_moreh_nll_loss.py with only the reader kernel reverted to main: 3 failed, 11 passed (80.96 s) at main versus 14 passed (24.42 s) with the PR kernel. The three failures are [2,10,2048] sum weighted (|got−ref| = 269.3), [2,10,4096] mean unweighted (0.248), [2,10,4096] mean weighted (461.5); with the fix they become 22.7, 0.0018, 0.0195. A five-case before/after regression suite (stock vs patched, identical results) covers the paths no upstream test touches.

Maintainer feedback. The tt-metal reviewer who handled this PR (bbradelTT) approved the change with a request: "Would you want to add a test to … that fails without this change and passes with it?" (review). He later asked for a rebase (comment) and confirmed that the visible CI failures (eltwise, deepseek) were pre-existing (comment).

What went wrong on the way, and what I left open. My first version of the test passed with and without the fix — it did not demonstrate anything — so I rebuilt it and reported the red/green counts with a fresh cache per variant. I explicitly recorded that the negative_ignore_index cases are not red on the simulator (an unallocated read returns 0, so 0 × garbage == 0 × 0), which means their red-on-hardware status is unverified. I also recorded that [2,10,8192] sum weighted is still wrong in both variants — it looks like a separate large-W defect and I deliberately did not encode it in the test rather than claim it fixed. I also isolated a CI failure that did not come from this diff: the repository's test-scoping script aborts while loading an unrelated vLLM matrix entry (Gemma3-27B [wh_llmbox], missing cmd), which cascaded into the "changed tests verified" gate.

2.2 #56202 — moreh_group_norm_backward: gamma_grad read the wrong group's statistics (item 5)

Status: merged (fce72e8, 2026-09-17) · pr-priority:p1, pr-risk:high, pr-complexity:low · 2 files, +64/−1

Symptom. gamma_grad was silently wrong whenever num_groups > 1.

Root cause. Pre-fix L129: mean_rstd_g_idx = c_idx % num_groups; where c_idx is the core-local channel index. The factory hands each core a contiguous channel block (tile_offset += num_channels_per_core * HtWt), so the global channel is outer_idx + tile_offset / HtWt — which is exactly what the sibling writer of the same op already computes (pinned blob, L52). Two consequences fall out of the wrong space: with the common one-channel-per-core split, c_idx == 0 on every core, so every channel read group 0's mean/rstd; and even single-core, C=8, G=2 yields groups 0,1,0,1,… instead of 0,0,0,0,1,1,1,1. The fetched mean/rstd feeds a broadcast subtraction in the compute kernel, so the entire gamma_grad is scaled by the wrong group statistics. The nightly test used C=4 with iid uniform data, where every group's mean ≈ 0 and rstd ≈ 0.866 — the error was masked.

Fix. Recover the global channel exactly as the sibling writer does, R130, and derive the group from it, R132. Both num_channels and num_groups are already runtime arguments, so no host-side change was needed. Plus a regression test, test_moreh_group_norm_backward_gamma_grad_group_index.

Measurement (ttsim, Blackhole, ttnn 0.78.0 — no hardware). With group 1's input scaled ×100 so the two groups' statistics are unmistakable: stock max|err| 4847.57 (G=2) and 4720.19 (G=4) versus 0.547 and 0.537 after the fix (bf16 rounding level). Element-wise at G=2, stock returned […, 2080.0, −4896.0, 3040.0, −2880.0] where the reference is […, 20.81, −48.43, 29.76, −28.05] — channels 0–3 (group 0) happened to be right, channels 4–7 were off by roughly two orders of magnitude. The reference was triple-checked: torch autograd ≡ closed form (|manual − torch| ≤ 2.3e-5). Reverting only the reader kernel makes the new test fail 8/8 against 8/8 passing with the PR kernel.

Maintainer feedback. bbradelTT: "Change looks good." with two requests — add a regression test, and remove the trailing Closes … because it can auto-close the umbrella issue even with text after it (review); approval after the follow-ups (review).

Revision worth noting. I did not just delete the line: I could not determine GitHub's exact parser rule, so I changed the verb to "Addresses …", said why, and offered to revert the wording. I also corrected a miscount in my own earlier comment about the test's parametrization axes rather than let it stand.

2.3 #56203 — moreh_arange: the row-major writer wrote 64 bytes past its buffer (item 3)

Status: merged (ecd6b8f, 2026-09-16) · pr-priority:p1, pr-risk:high, pr-complexity:low · 2 files, +25/−7

Symptom. With untilize_out=True (ROW_MAJOR output), arange corrupted the tensor the allocator had placed after its output — silently, and in the exact parametrization the nightly test already used.

Root cause. Pre-fix L25: uint32_t num_bytes_per_tile = TILE_WIDTH * element_size; — a fixed 128-byte chunk for fp32 — written for every work unit, including the last. A ROW_MAJOR interleaved output page is exactly num_elems * element_size long (the last dimension is not padded; the default alignment for an interleaved row-major page is {1}). For the nightly parametrization start_end_step=[10.9, −13, −0.3] (L=80, fp32) the buffer is 320 bytes, and the unconditional full-chunk write put chunk 3 at bytes [256, 384) — 64 bytes past the end. The sibling TILE writer is correct because a TILE output is padded to 32 in the last dimension; the RM writer reused that assumption where it does not hold. The test passed because nothing validated the clobbered neighbour.

Fix. Clamp the final chunk, with the bound computed host-side and passed down as a runtime argument — this was the reviewer's rework request, not my first draft: the factory computes last_chunk_width = ((W − 1) % TILE_WIDTH) + 1 and gates it to the core that owns the last tile (writes_last_chunk = (tile_offset + num_tiles_per_core) == Wt); the kernel reads it as runtime argument 6 and no longer derives anything from the accessor's page geometry. A follow-up commit deleted the now-dead num_bytes_per_tile.

Measurement (ttsim, Blackhole). Corruption probe: pre-allocate the RM output, place a sentinel guard tensor immediately after it, run arange into the pre-allocated output, read the guard back — 16 of 64 guard elements clobbered at stock (exactly the 64-byte overrun, holding arange tail values) versus 0 with the fix; the output values themselves are unchanged (max|err| 1.9e-06 both). Value regression across fp32/int32/bf16 shapes: 0 error, except 0.0625 for bf16 (rounding).

Maintainer feedback. bbradelTT: "Please have the appropriate width be created in the program factory and passed as a runtime argument to the kernel." (review) — then approval after the rework (review).

The limit I stated instead of hiding it. After the rework, the installed wheel's prebuilt host code still passes the original six runtime arguments while the reworked kernel reads index 6. Local end-to-end measurement would therefore have measured that mismatch, not the PR — so I said so and offered static coverage instead: for every W in 1..20000 the factory formula equals the true last-tile width, and for each W × core-count exactly one core is flagged with spans covering tiles [0, Wt) exactly once. This one needed CI, and I said that too.

2.4 #56334 — moreh_norm_backward for p = ±inf

Status: merged (43474e7, 2026-09-17) · pr-priority:p2, pr-risk:medium, pr-complexity:low · 3 files, +180/−0 · fixes #56248 (issue authored by me)

Symptom. The backward op returned garbage at the extremum for p = +inf and all zeros for p = −inf, although the forward op special-cases those orders.

Root cause. Pre-existing code, L37–L44: get_floored_p_and_decimal_and_p_is_negative floors p and casts the result to uint32_t unconditionally. For p = ±inf that cast is undefined behaviour ([conv.fpint] — 0 on this path), and decimal = p − floor(p) is inf − inf = NaN. The kernel's power ladder then computes x^(p−1) from a garbage exponent. The forward op's factories handle these orders explicitly (IS_ZERO / MINUS_INF defines); the backward factory had no equivalent.

Fix. Detect the order in the factory (if (std::isinf(p)), R259) and emit a NORM_INF define instead of feeding ±inf into the floored-exponent path (R260); the kernel then computes the exact sub-gradient in a dedicated branch, entered at R52: tmp4 = |x|, tmp5 = |x| − y, mask eq(tmp5, 0), sign(x) · dy, and finally dx = (sign(x) · dy) · mask. One branch covers both signs, because y is max|x| for +inf and min|x| for −inf, so only the equality matters. The finite-p ladder is untouched behind the #else, and a new regression test covers p ∈ {inf, −inf} × dims {N,C,H,W} with deliberately odd magnitudes so the PyTorch reference is unambiguous.

Measurement (ttsim, Blackhole, bf16, torch autograd reference). Every ±inf case: max|err| = 0 across 1-D, 2-D (row and column broadcast), and 4-D [5,8,78,77] over all four dims. Zero regression on the 138-case finite-order suite (p ∈ {2.0, 2.5, −2.5}).

Maintainer feedback. bbradelTT approved (review) and a rebase request (comment); I replied with the rebase and confirmed the patch itself was unchanged, and reported separately that the only failing pre-commit job was black formatting in the new test file.

Known limitation, stated in the PR. When |x| is tied across T elements at the extremum, torch splits dy evenly (dy/T each); this fix gives every tie member the full dy. Resolving ties exactly requires a cross-core reduction of the tie count, so it is noted as future work and the tests construct tie-free inputs — the divergence is explicit rather than latent.

2.5 #56074 — softmin: the last tile skipped the max subtraction (items 12 and 13)

Status: open, under review · pr-priority:p1, pr-risk:high, pr-complexity:medium · 2 files, +6/−2

Symptom. With the LARGE_W / LARGE_H parallelization strategies and op=SOFTMIN (the op's default mode — the forward factories emit the SOFTMIN compute define at five sites, e.g. one of them), the reduced sum was not 1: a row summed to 7.18 when the reduction fit one tile and to 1.71 with two tiles, i.e. the denominator mixed two different scales.

Root cause. In the last H/W tile, the softmin (non-softmax) branch exponentiated the raw input instead of (x − max), while every other tile and all of step 3 subtract the row/column max first. In the h kernel, the pre-fix branch went straight to rexp_tile_and_mask_tile_to_cb on the raw input.

Fix. Subtract the broadcast max first, then exponentiate: rows variant in the h kernel, cols variant in the w kernel. Two files, six added lines, no other path touched.

Measurement (ttsim, Blackhole, ttnn 0.78.0 — no hardware). Row/column sums before → after, expected 1.0: 7.18 → 0.992 (Wt==1), 1.71 → 0.999 (Wt==2); per-tile sum error 0.366 / 0.346 → 0.0009 / 0.0003; the SOFTMAX control path stayed at 0.989 (bit-identical, as its branches were not touched).

Maintainer feedback. None yet — the PR is waiting on review. The triage labels above were applied by the repository (minaliuTT), not claimed by me.

2.6 #56111 — moreh_sgd: tile counts from the logical shape, volume from the padded shape (item 11)

Status: open, under review · pr-priority:p1, pr-risk:medium, pr-complexity:low · 1 file, +1/−1

Symptom. For a TILE-layout parameter whose logical H/W are not tile multiples, the op processed too few tiles — or none — and silently left part of param_out (and momentum_buffer_out) unwritten.

Root cause. Pre-fix L46: auto shape = param_in.logical_shape(); while the work volume came from physical_volume(), which is padded. For logical [1,1,32,40] bf16, padded is [1,1,32,64]: num = 2048/32/40 = 1, Ht = 1, Wt = 40/32 = 1 → one unit of work, so only page 0 is processed and the real columns 32..39 (which live in page 1) are never written. For logical [1,1,30,32], Ht = 30/32 = 0 → zero units of work, and the output is never written at all.

Fix. One line: param_in.padded_shape(), which puts H, W, Ht, Wt and physical_volume() in the same units and matches every sibling moreh factory that uses the same idiom.

Measurement (ttsim, Blackhole, stock 0.78.0 wheel). The program factory is host-side code compiled into the wheel — not a JIT kernel — so the post-fix program for [1,1,32,40] (padded [1,1,32,64]) is identical to the program the same factory already emits for an aligned [1,1,32,64] tensor. Running that program on a manually padded tensor therefore reproduces the post-fix device behaviour on the unmodified wheel: wrong elements (atol 0.05, reference param − 0.1·grad) 242/1280 → 0/1280 for [1,1,32,40] and 917/960 → 0/960 for [1,1,30,32], with the aligned control unchanged at 0/2048. I also offered to add an unaligned shape to the nightly parametrize list, which is exactly how this slipped through.

2.7 #56197 — moreh_adam: wrong exponent units, plus a pack issued before its handshake (items 1 and 2)

Status: open, under review · pr-priority:p1, pr-risk:high, pr-complexity:medium · 1 file, +5/−5 (two independent commits)

Symptom. param_out was garbage — max|err| 3.03e16 against a torch Adam reference — and, tellingly, the output was bit-identical for step = 1, 2 and 10.

Root cause (a). power_tile(dst0, step) at L150 (and the same call at L259) passes the raw integer optimizer step where power_tile's param0 is documented as IEEE-754 float bits. Converter::as_float(1u) is 1.4e-45, so pow(beta, step) evaluated to 1.0 for every step, both bias corrections became recip(0) = inf, and the result was garbage that did not depend on step at all. This was the only remaining power_tile call in the tree after the API's contract changed without this kernel being updated.

Root cause (b). L223: in the sqrt(exp_avg_sq / bias_correction2) block the PACK thread issued pack_tile_with_dt() before tile_regs_wait(), so the pack read DST without the MATH↔PACK handshake while MATH was still writing that DST half — a timing-dependent stale read of cb_tmp1 that silently corrupts param_out. Every other block in the file (and every moreh_common.hpp helper) packs after the handshake.

Fix. Use the integer-exponent idiom the other moreh power sites use: site 1, and the same at site 2; and move the pack after the handshake.

Measurement (ttsim, Blackhole, ttnn 0.78.0 — no hardware). max|err| on param_out versus torch, bf16 (2,3,32,32): stock 3.03e16 / 3.03e16 / 3.03e16 (step 1/2/10); item (a) alone leaves ~2.3 (item (b)'s deterministic stale-DST error); both fixed gives 0.0010 / 0.00074 / 0.00049, with output mantissas matching the reference. Control: exp_avg and exp_avg_sq are byte-identical before and after, which is the expected signature — they touch neither power_tile nor the reordered block.

2.8 #56386 — softmin: the SOFTMIN define was emitted but never consumed (fixes #56371)

Status: open, under review · pr-priority:p2, pr-risk:medium, pr-complexity:low · 7 files, +321/−5 · issue authored by me

Symptom. Whenever the reduced dimension contained +inf, softmin returned all-zero rows (sum 0) where torch returns a valid distribution with 0 at the +inf position; −inf inputs also collapsed. It reproduced on every kernel path: small W, large W, H, both NC dims, and the masked/unaligned W path. No error was raised.

Root cause. The forward program factories emit the softmin compute define — compute_defines["SOFTMIN"] = "1", one of five such sites — but no kernel consumed it: grepping every forward and backward compute/dataflow kernel in the moreh_softmax* tree at the pre-fix commit finds zero occurrences of SOFTMIN, while the op's enum and signature do default to it. So the kernels computed the softmax statistic max(x) and negated the exponent — algebraically equal to softmin(x) = softmax(−x) only for finite input. With +inf in a row, max = inf overflowed every exp() and the row collapsed to zero.

Fix. The softmin branch now computes the minimum statistic, as min(x) = −max(−x) (the FPU has no bf16 MIN reduce): tiles are negated into the temp buffer with new moreh_common.hpp helpers, MAX-reduced with per-tile Accumulate folding, and the final post-reduce callback negates the accumulator back; masked padding lanes are written as +inf before the negate so they become −inf and can never win the max(−x) reduce — a zero-filled pad would win whenever every real lane is negative. The cross-tile fold in the c kernel switches to binary_min_tile directly. The change lands in five forward kernels: h, h_large, w, w_large, and c_large, with the branch structure visible at h and c_large.

Measurement (ttsim, Blackhole, no hardware; torch.nn.functional.softmin as reference). For one +inf per row: dim-3 W=32 → row sum 0 → 0.996 (max err 0.0045); W=128 (large-W path) → 0 → 0.975 (0.0025); dim-2 H=128 → column sum 0 → 1.0 (0.0047); NC paths → max err 0.36 → 0.024 and 0.55 → 0.022; unaligned W=33 (mask path) → sum 1.0. Full nightly suites with the patched kernels: test_moreh_softmin.py 104 passed / 32 skipped (bfloat8_b, official skip) / 0 failed, including the 12 new special-value cases; test_moreh_softmax.py + test_moreh_logsoftmax.py 185 passed / 64 skipped / 0 failed. New test: test_softmin_special_value_in_row, parameterized over six shape/dim combinations × {+inf, −inf}.

Documented divergence, not papered over. For a row whose only specials are −inf, torch produces NaN (IEEE inf − inf) while the SFPU evaluates inf − inf to 0, so the kernel returns a well-defined distribution concentrated on the minimum. That is the same class of divergence as the p = ±inf norm orders of §2.4. The regression test asserts the documented behaviour instead of asserting NaN.

3. What the work actually consisted of

These are the techniques that produced the results above, written so they can be judged (or reused) independently of the findings.

3.1 Use the in-tree sibling as the contract

For every defect in this set, the intended invariant was already written down somewhere else in the same repository, in a variant of the same operator: the 4d reader of moreh_nll_loss_step2 for the weight-guard pattern (§2.1), the writer of group_norm_backward for the global-channel arithmetic (§2.2), the TILE writer of arange for why one writer is right and its RM sibling wrong (§2.3), the forward moreh_norm factories' IS_ZERO/MINUS_INF handling for §2.4, and the power_iterative_tile call sites in moreh_common.hpp for §2.7. This matters for two reasons: it fixes the root cause rather than the observed symptom, and it means the PR can point a reviewer at the reference instead of arguing from authority. Where an in-tree reference did not exist, the alternative implementations are in the project's own test suite and in PyTorch.

3.2 Separate host code from device code before claiming a reproduction

The installed wheel contains compiled host-side factory code but JIT-compiles kernels from the source tree. That asymmetry decides what can be demonstrated locally, and each of the three cases below appears in this set:

  1. Kernel under test, host code unchanged — patch the kernel, keep a fresh TT_METAL_CACHE per variant, revert only that kernel to main for the red run (§2.1, §2.2, §2.5, §2.7).
  2. Factory change whose effect is a program the wheel already emits — the post-fix program for a padded-shaped input equals the program the wheel already emits for the aligned shape, so running that on a manually padded tensor reproduces the post-fix device behaviour on the unmodified wheel (§2.6).
  3. A factory/kernel contract change — then no local measurement is meaningful, because host and kernel are mismatched locally. §2.3 is the example: after the reviewer's rework, the wheel passed six runtime arguments while the kernel read a seventh, so I supplied a static proof over all W ∈ [1, 20000] and stated plainly that the end-to-end claim needed CI. Saying "this needs CI" is cheaper than a bad claim.

3.3 Make silent corruption visible

Correctness defects in this stack do not usually announce themselves — the op returns a tensor. Four probes recurred:

  • Sentinel guards. Pre-allocate the output, place a guard tensor immediately after it, read the guard back. This turns "64 bytes past the end of the buffer" into a count: 16 of 64 guard elements clobbered (§2.3).
  • De-masking the reference. Wrong-group reads and wrong-index reads are invisible when the reference data is uniform, so scale one group's input ×100 (§2.2) or make |x| magnitudes odd and unique so the PyTorch reference is unambiguous (§2.4).
  • Isolating two defects that compound. When two defects in the same kernel both corrupt the same output, fix them in separate commits and report the intermediate measurement, so the reviewer can attribute each residual (§2.7).
  • Controls. Every measurement set above includes a path the change does not touch (SOFTMAX, the aligned shape, exp_avg/exp_avg_sq), asserted unchanged — because "everything is green now" is not evidence if the baseline moved.

3.4 Red/green discipline, including admitting when the first test was worthless

A regression test is only evidence if it fails without the fix. My first version of the nll_loss_step2 test passed in both variants and demonstrated nothing; I rebuilt it, ran it with a fresh TT_METAL_CACHE per variant, and reported the counts either way (§2.1). In the same comment I recorded the two cases that stay green on both variants and why (the simulator returns 0 for unallocated memory, so the corruption pattern cannot be reproduced locally), rather than presenting a green suite as proof of a wild-read fix.

3.5 Report the shape of what you cannot verify

Each PR states its own boundary: the [2,10,8192] case that is still wrong and belongs to a different defect; the negative-ignore_index case whose red-on-hardware status is unverified; the tie behaviour of p = ±inf that needs a cross-core tie count; the factory/kernel mismatch that blocks a local run; the −inf-only divergence from IEEE semantics. This is not decoration: those paragraphs are what let a reviewer decide what to trust, and they are the reason a maintainer can merge without having to re-derive the boundary themselves.

3.6 The review loop is part of the artifact

Concretely, across these eight PRs: reworking a fix to move the bound into the program factory and passing it as a runtime argument (§2.3); dropping an auto-closing Closes/Fixes keyword because the referenced issue is an umbrella that must stay open, and saying that I was unsure of the parser rule instead of asserting it (§2.2, §2.1); rebasing repeatedly and reporting whether the rebase changed the patch (patch-id-identical) or was a re-roll (§2.1, §2.4); reporting a CI gate failure that came from an unrelated vLLM matrix entry rather than from the diff, with the failing run link (§2.1); and correcting my own miscount of a test's parametrization axes in a follow-up comment (§2.2).
